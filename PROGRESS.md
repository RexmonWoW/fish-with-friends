## Infrastructure in progress (not on the numbered list, but underlies it)
- Networking (`network_manager.gd`) — P2P host/client via GodotSteam, lobby create + host implemented. **First two real 2-machine tests done** (Steam invite/join), two rounds of genuine client-can't-play bugs found and fixed: (1) `MultiplayerSpawner.spawn_function` was only ever registered host-side, so a joining client's spawner had nothing to run when the host's spawn replicated over — every spawn silently failed on their machine. (2) Once (1) was fixed, the client's Player node genuinely existed and worked (they could cast), but ALL the spawn bookkeeping (`spawned_players` dict, the `spawned_local_player` signal `MainMenu` listens for to hide itself) lived inside a function only ever called host-side — so the client stayed stuck on the menu forever even though their player worked underneath, and `NetworkManager.spawned_players` was empty on their machine (which would've also broken `ReelMinigame` there, since it looks the caster up through that dict). Fixed with a split registration path: the host registers directly from its own `.spawn()` return value, every other peer registers via `MultiplayerSpawner`'s `spawned` signal on replication receipt — confirmed empirically (not assumed) that the signal does *not* fire for the peer that originates the call. Still substantial gaps beyond spawning — see Next Up.
- Player movement + equipment slots — RigidBody3D movement and equipment slot system in progress. Movement was near-frozen (plateaued ~0.2 m/s against a 5.0 m/s cap) because default RigidBody3D/StaticBody3D friction against the boat hull was eating almost all applied force — fixed with a low-friction `PhysicsMaterial` on both, plus retuned `move_force`/`linear_damp`. Verified with `tests/movement_smoke_test.gd`. Player visibility to other players fixed: `PlayerModel` was a completely empty node (no mesh — other players were invisible); now a capsule body tinted with a deterministic per-peer color. Also had to add `CameraRig`/`CameraPitch` rotation to `PlayerSync`'s replication so the held rod (now camera-attached, see item 5's session log) actually rotates to match a player's real aim direction for everyone watching, not just locally.
- Boat entity — just started. Currently a flat raft (hull only, no walls) per direction — the walls were also causing a hard full-stop on collision at speed.
- Lake map (`scenes/maps/lake.tscn`) — was a completely empty scene (no script, no children) as of session start. Now has a placeholder Environment/lighting, a large water plane in the `water_surface` group, the boat, livewell, `BiteEventManager`, and 4 player spawn points, enough to satisfy `Map._validate_contract()` and let casting be tested for real. Still placeholder box art — real geometry is Art & Polish's per the comment in `network_manager.gd`.

## Open Questions
_(design/scope questions that came up mid-build and need a call from the planning chat — log them here instead of guessing)_
- **Made a security-relevant call, flagging for visibility**: fixing the multiplayer gaps below required `FishData`/`CaughtFish` (Resources) to travel over RPC, which `SceneMultiplayer` refuses by default (`allow_object_decoding = false`) since decoding arbitrary Objects off the wire is a real attack surface on an untrusted network. Enabled it in `NetworkManager._allow_resource_rpcs()`, judged safe here because GDD scopes this game to Steam-friends-only P2P lobbies (not public matchmaking) and the resources involved are plain `@export` data with no side-effecting code. Worth a second look from planning if the trust model ever changes (public lobbies, matchmaking, etc.) — decomposing to primitive-field RPCs instead would be the safer-but-more-verbose alternative.
- `Rod.current_map` is set once, in `EquipmentSlot.equip_rod()`, from whatever `NetworkManager.get_current_map()` returns at that moment. For the host this is safe (map loads before players spawn), but a joining client's map-load RPC and their own player spawn/equip aren't ordered against each other, so a client could theoretically equip before their map finishes loading (current_map stays null → permissive fallback, not a crash, just unvalidated water for a frame). Not yet tested against a real second machine.
