QTE layer: the fish periodically "runs," prompting a SPACE/arrow key within ~1.1s; miss it and the zone shrinks; miss 3 times and the line snaps (fish gone, no catch). Zero misses on a catch = perfect, threaded through to `FishFactory`'s existing 1.5x value bonus (that plumbing already existed, nothing had ever set the flag). Verified with `tests/reel_qte_smoke_test.gd`.

[x] Line tangling + tug of war — two different players' `Rod.LineCollider`s (an Area3D that existed as an unused stub — fixed shape sitting at the rod's origin, representing nothing) now dynamically track the real line each frame and detect real overlaps. Crossing while both rods are `WAITING_BITE` starts a host-authoritative tug of war (`systems/tangle_manager.gd`): mash to push a shared rope value toward your side, first to the edge wins (6s timeout breaks a stalemate). Winner's line is untouched; loser's line snaps (`Rod` resets itself to `IDLE` on `EventBus.tangle_resolved`, same self-resetting pattern as reel resolution) and their pending bite is canceled. UI (`ui/tangle_minigame.gd`) shown to both involved players. Verified with `tests/line_tangle_test.gd` (real Area3D-detected crossing, correct winner/loser, loser's bite actually canceled).

Interaction is a consistent "one thing in hand at a time" loop: `E` stores whatever's held into the first empty slot, `1`-`5` grabs that slot's fish into your (empty) hands, `Q` tosses whatever's held from anywhere. Replacing a bad fish is grab-then-store (two explicit steps), not a direct overwrite. Livewell fish swim (a real per-slot circular loop, purely local/visual) instead of sitting static, and `LivewellDisplay` shows one fish's stats at a time -- whichever the local player is generally facing (within a deliberately generous 90° threshold, loosened from an original 14° that felt too fussy to track), closing the "proximity-only, not look-based" gap. ## Code Review Findings (planning-chat review, 2026-08-28)
_A full read of the actual `.gd`/`.tscn` files, not just this log — done because a session log can only report what its own tests happened to cover._

- **HIGH — FIXED (2026-08-28, same day as the review).** Root cause confirmed exactly as described. Fix taken was the review's "better" suggestion, not the minimal patch: removed `Rod.current_map` entirely rather than trying to keep a per-node cache correctly refreshed for every peer. `Rod._validate_and_land_cast` (already host-only code) now calls `NetworkManager.get_current_map()` fresh on every validation — nothing to go stale because nothing is cached. `tests/lobby_start_round_test.gd`'s old assertion tested the deleted mechanism, not the actual guarantee; replaced with a real regression test (spawn a second, non-local player after round start, validate their rod host-side, confirm the endpoint is genuinely snapped to real water height, not silently passed through unchanged). Full suite re-verified. Still not confirmed on a real second machine — that's next.
- **MEDIUM — reel outcome (win/loss/perfect) is entirely client-reported with no server-side plausibility check.** `Rod.request_reel_resolution(success, was_perfect)` validates *who* sent it, not whether the values are plausible — a modified client could always report a perfect catch. **Decision: accepted as-is.** Friends-only game per GDD, low stakes; not adding a server-side sanity check for now. Written down here so it's a deliberate trade-off, not an oversight. (Note: `TangleManager`'s mash-reporting has the same shape of trust — any peer can call `request_mash()` for themselves any time they're actually in a tangle, no rate limit beyond human input speed. Same trade-off, same reasoning, not calling it out as a separate open item.)
- **LOW — a couple of dead-code spots, not urgent**: `Fish.finalize_catch()` (`entities/fish/fish.gd`) is unused — the real catch path goes through `BiteEventManager` → `FishFactory` directly. `Rod`'s `RodSync` MultiplayerSynchronizer has an empty replication config (deliberately emptied in pass 9, never removed).
- **Resolved — the `allow_object_decoding` open question below**: checked the actual RPC surface. No `any_peer` RPC (client → host) accepts a Resource/Object argument; only host-authority broadcasts carry `FishData`/`CaughtFish`. Safe under the current threat model as reasoned below. One caveat the original note didn't have: this flag is *global* to `SceneMultiplayer`, not scoped to these specific RPCs — it needs re-review the moment *anything* untrusted enters the picture (public lobbies, mods, non-friend joins), not only "if new Resource RPCs get added."
- **Resolved — the map-load-race open question below**: turned out to be worse than originally described — see the HIGH finding above. Not a rare timing window; currently a deterministic, always-on gap for every client under the lobby flow added in pass 13.
- **Overall read**: solid for two days of solo/duo work — consistent style, genuinely host-authoritative architecture, and the session log's bug descriptions check out against the real code. The recurring pattern worth naming: every real multiplayer bug this session (including the HIGH one above) has come from code that only gets exercised by a second real peer, and the smoke-test suite is structurally solo/single-process so it can't catch that class of bug on its own. That's not a criticism of the tests — they've caught real regressions — just a reason to treat "passes headless" and "confirmed on two machines" as two different bars, especially right after a change like the lobby rework that touches per-peer state.

## Open Questions
_(design/scope questions that came up mid-build and need a call from the planning chat — log them here instead of guessing)_
- **Economy model (new, 2026-08-29)**: GDD specifies personal wallets (haul split equally, buys personal upgrades) plus a separate voluntary shared boat fund (buys the fish finder only). Implementation currently has one shared pot only. Needs a planning call before the Per-Run Shop gets built: keep the single-pot model for now (simpler, but diverges from GDD and shop items would need rethinking), or switch to personal wallets + shared fund before shop work starts (matches GDD, but is rework on top of the existing quota/pot code).
- **"Free days" from quota banking (new, 2026-08-29)**: confirm whether it's intended that a big enough early haul can clear a future day's quota with zero new catches that day (cumulative total vs. a fresh per-day threshold), or whether quota should reset/require fresh earnings each day instead.
- **Quota balancing** — GDD.md now specifies the adaptive formula itself (`next_quota = round(previous_quota * 1.15 + surplus * 0.4)`), implemented as of 2026-08-29. `BASE_QUOTA=100`, the `1.15` daily growth, and the `0.4` surplus factor are still GDD's own placeholder numbers pending real balancing against actual expected catch income — not yet checked against `FishFactory`'s value formula or realistic per-round catch rates. **RESOLVED (formula itself) — numbers still open.**
- **Big Fish Event tunables (new, 2026-08-29)**: GDD's spec is detailed on mechanics but doesn't give exact numbers for trigger frequency, join radius, event duration, or QTE-miss penalty size. Picked, all in `systems/big_fish_event_manager.gd`: ~8% chance every 30s during a round (roughly one attempt per round), 4m join radius, 45s once active, self-miss -0.22/shared-miss -0.08 (out of a 0-1 bar). Needs real playtesting, not just "feels plausible on paper."
- **Big Fish Event team-catch credit (new, 2026-08-29)**: GDD doesn't say who gets "caught by" credit for a shared catch. Went with a literal "The Crew" instead of picking one participant arbitrarily — reasonable given "it's a team moment," but worth an explicit yes/no, especially once a Steam leaderboard (biggest fish ever caught) exists and needs a real attribution model.
- **Made a security-relevant call, flagging for visibility**: fixing the multiplayer gaps below required `FishData`/`CaughtFish` (Resources) to travel over RPC, which `SceneMultiplayer` refuses by default (`allow_object_decoding = false`) since decoding arbitrary Objects off the wire is a real attack surface on an untrusted network. Enabled it in `NetworkManager._allow_resource_rpcs()`, judged safe here because GDD scopes this game to Steam-friends-only P2P lobbies (not public matchmaking) and the resources involved are plain `@export` data with no side-effecting code. Worth a second look from planning if the trust model ever changes (public lobbies, matchmaking, etc.) — decomposing to primitive-field RPCs instead would be the safer-but-more-verbose alternative. **RESOLVED — see Code Review Findings above.**
- `Rod.current_map` is set once, in `EquipmentSlot.equip_rod()`, from whatever `NetworkManager.get_current_map()` returns at that moment. For the host this is safe (map loads before players spawn), but a joining client's map-load RPC and their own player spawn/equip aren't ordered against each other, so a client could theoretically equip before their map finishes loading (current_map stays null → permissive fallback, not a crash, just unvalidated water for a frame). Not yet tested against a real second machine. **RESOLVED (and worse than described) — see Code Review Findings above.**
